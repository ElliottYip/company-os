# 团队第六课：完成变更与责任移交

## 学习结果

学生能把 Agent 工作从项目团队移交给长期所有者，验证能力、权限、值班、文档、评测、回退与退役路径。

## 核心概念

上线不是移交。长期团队必须能独立运行、解释、接管、更新和停止系统；开发者仍在旁边救火说明责任尚未真正转移。

## 决策框架

明确未来所有者与受影响人员；移交结果合同、Skill/版本、数据与身份清单、评测集、运行卡、事故路径、供应商依赖和退出计划；通过演练验证接管，而不是以文档签收代替能力。

## 来源

- `[CLM-016]` 与 `[SRC-OECD-WORKPLACE-CASES-2023]` 支持早期员工参与、训练和对任务变化的观察。
- `[CLM-013]` 支持维持真人理解、控制和接管能力。
- `[CLM-014]` 支持持续监测、变更管理和安全退役。
- `[CLM-023]`、`[CLM-024]`：`[SRC-OUT-OF-LOOP-1995]` 与 `[SRC-AUTOMATION-TEAM-PLAYER-2004]` 支持通过主动演练维持态势感知和协调能力；现代 Agent 迁移结论仍需本地验证。

## 讲授

移交演练应让长期团队在没有开发者代答的情况下处理权限过期、评测回归失败和结果未知。失败不是丢脸，而是指出尚缺的训练、工具或职责。退出计划包括撤销凭据、停止任务、保留必要记录、处理数据和恢复原流程。

### 决策推演：文档齐全不等于能力已经转移

接收团队需要证明能识别异常、取得正确证据、执行暂停或回退、联系责任人并安全恢复。最有效的检查不是让开发团队演示，而是让接收者在受控故障中独立操作，开发者只观察。若接收者必须依赖未记录的个人知识，移交结果应标为未通过，并把缺口回写到运行卡、Skill 或责任图。

移交还要覆盖变化。模型、供应商、工具 schema、数据政策和业务口径更新时，谁触发回归、谁批准新版本、旧版本保留多久、存档如何迁移，都应有明确路径。否则系统在上线当天可运行，却会在第一次依赖更新后失去所有权。

退役是最后一种变更。停止调度只是第一步，还要撤销身份与审批、处理队列中的工作、保留必要审计记录、删除不再需要的数据副本、通知依赖方并验证原流程或替代方案恢复。无法安全停止的系统，不应被视为完成长期治理。

## 失败模式与边界

- 只交一份操作文档；
- 没有替补、值班和升级联系人；
- 模型或供应商变化后不跑回归；
- 停用 Agent 却保留长期凭据和数据副本。

## 实操

完成移交清单并运行三题演练：权限过期、质量回归、外部动作结果未知。记录长期所有者能否独立处置。

## 完成证据

- `developing`：有明确长期所有者和回退；
- `capable`：能移交评测、身份、运行和事故材料；
- `strong`：能以演练证明独立接管与安全退役。

## 降级路径

使用合成团队桌面演练，不变更真实值班或权限。

## 下一节点信号

- 移交通过：进入持续运营；未通过则返回责任、运营或治理节点补缺口。
