# 治理第六课：分开身份、凭据与业务授权

## 学习结果

学生能设计 Agent、用户和服务身份，防止 Secret 暴露、token 透传与跨受众复用，并说明身份认证不等于动作批准。

## 核心概念

身份回答“谁在调用”，凭据是证明身份的秘密材料，scope/audience 限制技术访问；结果合同与精确审批决定当前业务动作是否获准。

## 决策框架

为每个连接标明主体、目标受众、最小 scope、存储位置、有效期、轮换/撤销、日志脱敏和下游换证。模型上下文不得出现原始 Secret；上游 token 不透传给下游服务。

## 来源

- `[CLM-011]` 与 `[SRC-MCP-AUTH-2025-06]` 支持 audience 校验、禁止 token passthrough、安全存储、短期 token 与 PKCE。
- `[CLM-009]` 支持最小权限和影响半径收缩。

## 讲授

一个有效 token 只证明调用者获准访问对应资源服务器，不证明“可替用户付款”。工具运行时可持有凭据，模型只看到有界工具接口。需要调用下游 API 时，应取得面向下游的独立 token，而不是转发收到的 token。

### 决策推演：身份链必须能被撤销和归因

用户、Agent 运行时、工具服务和下游 API 可能是四个不同主体。若它们共享一个长期管理员 token，日志无法说明谁发起动作，撤销也会同时破坏无关工作。每条边都应有面向目标服务的 audience、当前工作需要的 scope、明确期限和凭据持有者；模型只请求有界动作，不读取秘密值。

“代表用户”不等于转发用户 token。下游服务应看到为它签发且能识别调用链的凭据；上游 token 的 audience 不匹配时必须拒绝。业务层还需要保存原始请求者、执行 Agent、工具主体和审批人的关系，以便事后回答谁提出、谁批准、谁执行。认证成功只解决其中一部分。

Secret 泄露响应包括定位暴露副本、撤销或轮换、检查使用记录、清理非必要日志与缓存、验证新凭据生效。仅从 prompt 删除字符串不能使已发出的凭据失效。课程练习永远使用占位符，因为把真实 Secret 交给导师或测试脚本本身就是边界失败。

## 失败模式与边界

- 把 Secret 放进 prompt、RAG 或 trace；
- 多个 Agent 共用长期管理员 token；
- audience 不匹配仍接受；
- 把登录成功当作高风险动作批准。

## 实操

绘制身份链：用户、Agent、MCP/工具服务、下游 API；为每条边填写凭据持有者、audience、scope、期限、撤销和业务审批点。

## 完成证据

- `developing`：能区分凭据与授权；
- `capable`：能设计最小 scope、audience 和换证；
- `strong`：能覆盖撤销、日志脱敏与高风险审批。

## 降级路径

只使用占位符，不创建或展示真实凭据。
