# 治理第二课：分开身份、授权与审批

## 学习结果

学生能为一项工作建立最小权限表，区分技术身份、工作授权和高影响动作审批，并识别过量功能、权限与自治。

## 核心概念

身份回答“谁在调用”，工作授权回答“这次可以做什么”，精确审批回答“这个具体高影响动作是否允许执行”。三者不能互相替代。

## 决策框架

从零权限开始，按每项工作列出必要数据、工具、动作范围、资源对象、时间窗和最大副作用。能只读就不写，能限定对象就不全库，能短期就不长期；高影响动作即使已在允许列表也要单独审批。

## 来源

- `[CLM-009]` 最小化功能、权限和自治：`[SRC-OWASP-EXCESSIVE-AGENCY-2025]`、`[SRC-NIST-GENAI-600-1]`。
- `[CLM-011]` 协议认证不等于业务授权：`[SRC-MCP-AUTH-2025-06]`。

## 讲授

一个 MCP token 能访问工具，不代表 Agent 获准为这项客户工作调用它。反过来，结果合同允许“起草邮件”，也不能让没有正确技术身份的进程越过认证。

权限设计还要考虑组合风险：单个“读联系人”和“发邮件”看似普通，组合后可向整本通讯录发送内容。审核最小权限时必须看能力组合和最大影响半径。

### 决策推演：最小权限是按工作计算的

角色级权限通常仍然过宽。“销售 Agent”这个角色无法说明它在本次工作中能读取哪个客户、向谁写入、持续多久。工作授权应绑定结果合同、资源集合、允许动作、数量或金额上限和到期时间；技术身份再把这些限制落实到工具层。若工具只能提供全库管理员能力，即使 prompt 里写了范围，也不能称为最小权限实现。

组合风险需要画能力链。读取客户名单、生成内容和发送邮件分别看似低影响，组合后却形成批量外联；读取内部文件、访问网页和上传附件组合后形成外泄路径。审查时不仅问“每项权限是否必要”，还要问“这些权限能组成哪些未声明结果”。可以通过分离身份、分阶段签发、运行时策略或精确审批打断危险链。

撤销是授权设计的一部分。工作结束、目标变化、Agent 改派、人员离岗或事故发生时，应能识别并撤销本次凭据与未消费审批。无法确定权限是否仍有效时，系统应默认停止高影响动作，而不是让模型根据历史上下文推断。

## 失败模式与边界

- 给共享管理员账号，再靠 prompt 要求谨慎；
- token passthrough 让下游误以为请求来自可信服务；
- 权限永久存在，不随工作结束撤销；
- 最小权限降低影响半径，但不能修复错误业务规则或被盗身份。

## 实操

为市场简报列一个权限表：数据、工具、读写、对象、时限、审批和撤销。删除所有“以后可能用到”的权限。

## 完成证据

- `developing`：能区分身份和授权；
- `capable`：能限定资源、动作和时间；
- `strong`：能识别组合权限和精确审批点。

## 降级路径

只做设计练习，不创建 token 或连接器。
