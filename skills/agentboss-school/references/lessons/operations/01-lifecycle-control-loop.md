# 运营第一课：建立生命周期控制闭环

## 学习结果

学生能为 Agent 工作定义从分配到验收的状态、观察、停止和升级规则，避免把“模型回复完成”当成真实完成。

## 核心概念

最小闭环是：目标与合同 → 计划 → 动作 → 环境观察 → 状态更新 → 接受、继续、暂停、升级或终止。状态必须区分运行中、等待输入、等待审批、成功、失败、取消和结果未知。

## 决策框架

对每个阶段回答：谁可以推进、什么证据允许转移、最长等待多久、何时暂停、怎样恢复、哪个终态不可自动重开。把外部环境观察放在 Agent 自述之后。

## 讲授

Agent 说“邮件已发送”只是一条输出。完成证据可能是邮件服务返回的消息 ID，并且仍需考虑服务超时后状态未知。控制闭环把“模型想做什么”“工具返回什么”“业务最终接受什么”分开记录。

停止条件同时控制风险和成本：达到结果、证据不足、重复失败、预算耗尽、授权过期或出现未声明动作时都应退出当前执行路径。

### 决策推演：状态必须互斥且有证据

`WAITING_FOR_INPUT` 与 `RUNNING` 不能同时成立，否则超时和责任人都不清楚；`FAILED` 与 `OUTCOME_UNKNOWN` 也不能合并，因为前者允许按策略重新开始，后者可能已经产生副作用。状态设计应优先表达下一控制动作，而不是复刻框架内部事件。模型生成了一段文本、工具开始调用、队列完成消费都只是活动，只有满足转移条件才改变业务状态。

每条转移至少绑定四件事：触发事件、可验证证据、允许推进的主体、超时后的去向。例如 `AWAITING_APPROVAL → EXECUTING` 需要未过期的精确审批，并且执行输入摘要与审批摘要一致；如果审批期间动作内容改变，应该回到待审批，而不是沿用旧许可。恢复时加载的也不是“最近一条消息”，而是最后一个可信状态、已发生副作用和仍有效的合同。

终态是否可重开必须由业务语义决定。被取消的市场简报可以新建工作，但不应静默复活原任务；已结算付款不能因评测分数下降而重新执行。把“新工作”与“原工作的恢复”分开，是避免重复动作和审计混乱的基础。

## 失败模式与边界

- 用一个 `success` 覆盖部分完成与结果未知；
- 没有最大步数、时间或成本；
- 恢复时丢失先前动作，造成重复副作用；
- 状态机可控不等于业务结果正确。

## 实操

为“生成并发布简报”画状态图，必须包含等待审批、拒绝、过期和结果未知四个非顺利分支，并写出每条转移证据。

## 完成证据

- `developing`：能列主要状态；
- `capable`：能为转移绑定证据与责任；
- `strong`：能处理恢复、终止和结果未知。
