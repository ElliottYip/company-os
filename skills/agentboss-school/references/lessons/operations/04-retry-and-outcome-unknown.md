# 运营第四课：处理重试与结果未知

## 学习结果

学生能识别“请求失败”和“动作结果未知”的差别，并为非幂等副作用设计查询、对账、幂等键或人工恢复路径。

## 核心概念

超时表示调用方没收到明确结果，不表示服务端没执行。`OUTCOME_UNKNOWN` 是需要调查的业务状态，不应被普通失败覆盖。

## 决策框架

重试前依次问：动作有副作用吗、服务是否支持真正的幂等语义、能否查询最终状态、请求意图是否完全相同、重复后果能否承受。任一答案不确定，就暂停、对账或人工接管。

## 讲授

读操作通常可以安全重试；发布、付款、创建账号和发消息未必。幂等键不是万能锁：如果相同键被复用于不同金额或新业务意图，系统应拒绝而不是返回旧结果。

恢复记录应保留原动作标识、请求摘要、尝试、最后已知状态、查询证据、责任人和最终处置。禁止 Agent 自己猜测“应该没执行”并重新发起。

### 先按副作用分类，不按错误码分类

网络层的 `timeout`、`5xx` 或连接断开，只说明调用方观察到了什么，不说明业务世界发生了什么。读取报表超时，通常可以重新读取；付款超时，则可能已经扣款但响应丢失。两者收到同一个错误码，恢复策略却完全不同。

因此先问动作是否改变外部状态。没有副作用的读操作可以在预算内重试；可幂等写入只有在服务端明确支持业务幂等、相同意图可被识别时才重试；非幂等动作优先查询最终状态、对账或转人工。

### 幂等键必须绑定业务意图

一个随机 request ID 只能标识请求，不自动保证业务幂等。可靠语义要求服务端持久记录该键与动作意图，并在重复请求时返回原结果或拒绝内容变化。付款金额从 1000 改成 1200，哪怕调用方复用了旧键，也不再是同一意图；系统不能把旧成功静默套到新请求上。

对消息发送、账号创建或外部发布，如果目标系统没有可查询状态和幂等保证，Agent Boss 应把这种限制写进结果合同：超时后进入 `OUTCOME_UNKNOWN`，停止自动动作，等待负责真人核对。

### `OUTCOME_UNKNOWN` 不是一种失败文案

它应成为独立状态，因为它限制后续动作。处在这个状态时，系统可以查询、收集证据和升级，但不能重新提交原副作用，也不能把工作标成失败后自动重开。只有拿到环境证据，才能转为成功、未执行、部分完成或需要补救。

发票主线中，支付接口在提交后超时。正确顺序是：冻结同一付款意图，保存动作摘要和幂等键，查询支付服务；若无明确结果，核对银行或账务记录；由财务责任人决定是否补救。错误顺序是：Agent 看到超时，立即生成一个新请求再付一次。

### 示范工作件：结果未知恢复记录

```text
工作：invoice-demo-017（合成教学情境，不是真实付款）
原动作：向供应商账户支付指定发票金额
业务意图摘要：发票号、收款方、金额、币种、批准绑定的摘要
尝试：1 次；提交时间 10:03；客户端超时
最后已知状态：OUTCOME_UNKNOWN
允许动作：查询支付状态、读取获准对账记录、升级财务负责人
禁止动作：创建新付款、修改金额后复用旧批准、猜测未执行
待补证据：支付服务最终状态或对账凭证
负责真人：财务责任人
最终处置：待证据确认后填写，并保留决定依据
```

这张记录让接管者看见已经发生过什么，避免“人工接管”变成从零猜测。

## 失败模式与边界

- 所有网络错误统一指数退避重试；
- 把客户端 request ID 当成业务幂等的充分证明；
- 人工接管时看不到已发生的尝试；
- 对账后更新状态，却没有记录依据。

## 实操

对读取报告、发布文章、付款和创建账户四个动作分别选择：直接重试、带幂等键重试、先查询、人工对账或禁止重试，并写理由。

## 完成证据

- `developing`：知道超时不等于未执行；
- `capable`：按副作用选择恢复策略；
- `strong`：能设计证据完整的结果未知处置记录。
