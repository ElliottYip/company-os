# 运营第三课：用评测与业务验收判断能力

## 学习结果

学生能设计一个包含任务集、重复 trial、评分器、环境结果和失败分析的最小评测，并区分能力分数与上线决定。

## 核心概念

评测对象包括任务、trial、agent、环境、trace、outcome 和 grader。评分器可由代码、模型或真人组成；最终上线还要考虑风险、成本和未覆盖条件。

## 决策框架

先写要支持的决策，再收集正常、边界、拒绝和对抗任务。定义确定性检查优先的 rubric；对随机执行重复 trial；按失败类型而非只按平均分分析；任何变更都跑回归。

## 讲授

“十个案例九个看起来不错”没有说明任务代表性、重复次数、政策违规或环境是否真的改变。最小评测报告应展示数据集版本、模型/工具版本、试验条件、评分规则、分项结果、失败样本和局限。

模型评分器适合扩大覆盖，但高风险规则优先用代码验证，主观质量需要经校准的人评。评测不是一次考试，而是变更前后的回归护栏。

### 从上线决定倒推评测

评测的起点不是“我们能测什么”，而是“结果会支持哪个决定”。要决定能否用于内部草稿，与要决定能否自动对外发布，需要完全不同的任务覆盖和错误容忍度。前者可能允许风格波动，后者必须把来源伪造、数字错误和越权发布作为阻断项。

一个可运行的最小评测包含七个对象：版本化任务集、每项任务的输入条件、被测 Agent 与工具版本、可重置环境、完整 trace、环境 outcome、一个或多个 grader。缺少环境 outcome 时，Agent 说“操作成功”不能当作成功；缺少版本信息时，回归结果无法比较。

### 任务集需要覆盖什么

只收集正常任务会高估能力。市场简报主线至少要覆盖四类：

1. **正常**：数据完整、来源一致，检查基本能力；
2. **边界**：数据缺失或来源冲突，检查能否报告不确定；
3. **拒绝**：要求读取未授权材料或直接发布，检查能否守住边界；
4. **对抗**：外部文档夹带指令，检查数据与指令是否分离。

任务数量不必一开始很大，但每个任务必须代表一个可能改变上线决定的失败面。真实运行中新出现的失败，应先匿名化、最小化，再决定能否成为回归案例。

### 三类评分器怎样分工

- **代码 grader** 检查可确定的规则：是否有来源、是否越过字数、是否调用禁止工具、环境记录是否存在；
- **模型 grader** 扩大语义质量覆盖，例如摘要是否忠实，但需要用人评样本校准；
- **真人 grader** 处理业务判断、风险接受与主观质量，同时需要清楚 rubric，避免每个人凭感觉打分。

一个总分会掩盖阻断性失败。即使平均分很高，只要出现一次未经批准的发布，当前自治模式也不应通过。报告应同时展示通过率、阻断项、失败分类、成本与延迟，而不是把它们压成一个漂亮数字。

### 随机性与重复 trial

Agent 执行具有随机性，一次成功只说明“这一次成功”。对关键任务重复运行，可以看到偶发失败和尾部行为。重复次数不是越多越科学；应根据风险和资源选择，并如实说明样本限制。调提示词、换模型、改检索、增工具或改权限后，都应在同一冻结任务集上回归。

### 示范工作件：最小评测卡

```text
上线决定：是否允许 Agent 生成内部市场简报草稿；不得发布。
任务集 v1：2 正常、2 边界、1 拒绝、1 注入。
每项 trial：3 次；保留全部结果，不挑最好一次。
代码检查：每条数字有来源；未调用 publish-content；输出标明数据日期。
人工 rubric：结论是否由来源支持；不确定是否被明确表达。
阻断项：伪造来源、读取范围外数据、尝试发布。
报告：分任务通过、失败类型、成本、P95 延迟、未覆盖条件。
决定：阻断项为零且边界任务达标，才进入受限试点；否则收紧或回退。
```

注意：这是一份评测设计示范，不包含真实分数，也不能证明某个 Agent 已经可靠。

## 失败模式与边界

- 只保留最好输出；
- 训练集、提示调优集和最终测试集混用；
- 用模型评价自己且不校准；
- benchmark 分数直接外推真实团队、权限和数据环境。

## 实操

为市场简报设计六个任务：两个正常、两个边界、一个拒绝、一个注入。定义至少两个代码检查、一个人工 rubric 和每项三次 trial 的报告格式。

## 完成证据

- `developing`：能写任务和成功标准；
- `capable`：能组合 grader、重复 trial 并分析失败；
- `strong`：能把评测结果转成上线、收紧或回退决定。

## 降级路径

只写评测计划与模拟结果；禁止编造真实分数。
