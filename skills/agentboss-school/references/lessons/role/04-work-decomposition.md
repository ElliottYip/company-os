# 角色第四课：按控制边界拆工作

## 学习结果

学生能把一项端到端工作拆成信息获取、分析、决定和动作阶段，并为每段选择真人、规则或 Agent 控制。

## 核心概念

工作拆分不是把任务平均切小，而是暴露不同的验收性、权限和异常代价。同一流程可以同时包含确定性自动化、Agent 委派、真人决定和高风险审批。

## 决策框架

按“输入 → 分析 → 建议 → 决定 → 执行 → 验证”画出流程；逐段标明输入来源、可检查输出、副作用、失败信号和责任人。边界稳定、规则明确的段优先用代码；需要开放探索但可验收的段才考虑 Agent；价值判断和不可接受后果留给真人。

## 讲授

以供应商付款为例：“处理发票”不应整体交给 Agent。读取获准邮箱、提取字段、匹配采购单、生成差异说明、决定是否付款、执行付款、对账，各段风险完全不同。字段校验可用规则；差异解释可由 Agent 起草；例外批准由真人负责；付款需要精确绑定；银行状态必须另行验证。

拆分后的价值是把自治限制在可验证区域，而不是增加更多 Agent。每段都应有输入、输出和交接条件，防止上游猜测被下游当成事实。

### 决策推演：拆到哪里才停止

拆得过粗，隐藏了不同权限与错误代价；拆得过细，又会让每次交接产生语义损失、延迟和责任空洞。停止拆分的实用条件不是“步骤足够小”，而是同一段内已经具有相同的控制者、权限等级、验收方法和失败处置。如果一段同时包含“提出建议”和“执行不可逆动作”，就还没拆到控制边界；如果两个相邻步骤总由同一规则执行、共享同一证据并共同失败，继续拆只会增加接口。

交接必须传递事实状态而不是自然语言印象。例如上游不写“供应商看起来正常”，而写数据来源、匹配字段、差异项、置信限制与尚未核实内容。下游只能消费声明过的字段；缺字段就回到等待或澄清，不能补猜。这样拆分既服务架构，也服务责任追踪。

一个反例是把招聘筛选拆成“简历 Agent、评分 Agent、排序 Agent、通知 Agent”，却让最早的评分悄悄决定谁被排除。Agent 数量增加了，真正的高影响决定仍被埋在上游。正确做法是把证据提取、规则检查、候选比较、真人决定和沟通动作按影响边界分开，并让拒绝决定有独立依据与责任人。

## 失败模式与边界

- 按部门或工具拆，而不是按结果与控制边界拆；
- 每一段都安排一个 Agent，制造消息损耗和故障面；
- 上游低置信度输出没有显式传递；
- 本方法不能替代行业流程、安全或财务控制设计。

## 实操

选一个不敏感任务，画出六段流程。至少指出一段规则化、一段 Agent 辅助、一段真人保留，并解释相邻交接的证据。

## 完成证据

- `developing`：能拆出不同阶段；
- `capable`：能按验收、权限和后果分配控制；
- `strong`：能设计交接证据并减少不必要 Agent。

## 降级路径

使用“发票处理”虚构情境，不连接邮箱、财务系统或真实数据。
