# 角色第六课：选择工作流、单 Agent 或多 Agent

## 学习结果

学生能用控制确定性、任务耦合、权限隔离和本地评测证据选择架构，并拒绝“Agent 越多越高级”的假设。

## 核心概念

- **工作流**：路径由代码预定义；
- **单 Agent**：一个模型动态选择过程或工具；
- **多 Agent**：多个角色通过消息或共享状态协调。

## 决策框架

先尝试单次模型调用或确定性工作流；需要开放规划时用单 Agent；只有当角色专长、权限隔离、并行性或上下文隔离的收益能被评测，且协调成本可接受时才用多 Agent。升级前记录基线、失败类型、成本和延迟。

## 讲授

多 Agent 会增加交接歧义、上下文重复、权限面、成本和故障组合。它也可能带来价值，例如并行独立研究、严格角色权限隔离、不同领域专家或长上下文分区。关键不是角色故事是否漂亮，而是相对基线是否改善最终结果。

AutoGen 的高星与维护状态提醒我们：社区关注度不等于当前推荐。框架 API 不进入课程规范，架构模式需能被替换。

### 三种结构不是成熟度阶梯

把工作流、单 Agent、多 Agent 画成从低级到高级的阶梯，会直接诱导错误设计。它们解决的是不同的不确定性。

- 路径清楚、异常有限时，工作流把决定写在代码里，便于测试和恢复；
- 路径无法预先穷举，但工具和结果边界清楚时，单 Agent 可以动态规划；
- 工作确实能拆成相对独立的专业域，且并行、权限或上下文隔离带来可测收益时，多 Agent 才值得进入候选。

以客服主线为例。订单状态查询、退款条件校验和模板回复都有确定路径，先用工作流即可。如果要让系统处理用户多轮描述中的歧义，可以在受限工具集上加入一个单 Agent。只有欺诈调查与普通客服必须由不同身份、不同数据权限处理，或大量独立案件可并行时，才出现真正的多 Agent 理由。“让一个 Agent 当经理、三个 Agent 开会”本身没有提供隔离或能力。

### 协调税怎样出现

每增加一个 Agent，不只是多一次模型调用，还新增了一个交接协议。上游需要说明它知道什么、不知道什么、用了哪些来源、置信度如何；下游要判断这些信息能否信任。若双方共享同一个错误来源，互相评审只会把错误说得更有共识感。

协调税至少体现在五处：消息转换、上下文重复、权限组合、终止判断和故障定位。多 Agent 的收益必须覆盖这些税，且不能只比较“看起来更完整”。应比较最终任务成功、政策违规、成本、尾部延迟和恢复难度。

### 架构升级是实验，不是重写冲动

正确的升级路径是保留同一任务集，先跑最小基线，再只改变一个结构变量。若单 Agent 经常因为上下文相互污染而失败，可以测试把研究与执行隔离；若只是输出格式不稳定，增加 Agent 往往不如确定性校验。

升级前写清触发条件，例如：“在固定评测集上，研究和核验并行使通过率提高，同时每任务成本不超过预算、严重政策违规为零，才进入有限试点。”如果证据不成立，回退到基线，而不是继续给角色加名字。

### 示范工作件：架构决策记录

```text
工作：处理已授权知识库内的客服查询，不执行退款。
最小基线：确定性路由 + 单 Agent 检索与起草。
不选纯工作流：自然语言问题存在未穷举歧义。
暂不选多 Agent：没有独立权限域；预计协调成本高于并行收益。
主要故障：错误检索、来源过期、越权承诺。
比较指标：任务通过率、越权率、单任务成本、P95 延迟。
升级证据：出现可重复的专业域冲突，且隔离实验改善结果。
回退条件：严重违规、成本越界或延迟超过服务目标。
```

这份记录的核心不是“选择了什么”，而是保留当时为什么选择、用什么证据改变决定。框架可替换，决策逻辑应留下。

## 失败模式与边界

- 用角色名称代替真实权限隔离；
- Agent 相互评审却共享同一错误来源；
- 没有终止条件，讨论循环消耗成本；
- 仅凭 demo、star 或供应商声明选择架构。

## 实操

对同一任务写三种方案，各列一个收益、两个新增故障面和一个比较指标。选择最小方案，并写明何种证据会触发升级。

## 完成证据

- `developing`：能区分三种控制方式；
- `capable`：能依据任务与风险选择；
- `strong`：能定义升级实验和回退方案。

## 降级路径

只做纸面设计，不安装任何 Agent 框架。
