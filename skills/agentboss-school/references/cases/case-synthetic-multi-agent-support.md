# 合成案例：五个客服 Agent 不如一个受控工作流

> **SYNTHETIC_SCENARIO / ILLUSTRATIVE**：本案例中的组织、角色、事件、系统、数据和结果均为虚构，只用于教学。它不是客户案例，也不是框架性能比较。

## 业务背景

一家虚构订阅软件团队想处理“重复扣费”工单。初版方案安排分类、政策、情绪、退款和质检五个 Agent 相互传话，希望用角色分工获得更专业的结果。

## 原始工作方式

客服专员核对订单和付款状态，按明确政策决定是否提出退款，高金额或身份不一致时升级给主管。真正难点是工具状态与政策例外，不是写出礼貌回复。

## Agent 工作设计

团队先做三种纸面和离线方案：确定性工作流、单 Agent 加受限工具、五 Agent 协作。共同结果合同要求确认客户身份、读取指定订单、解释政策、不得自行退款，并输出支持决定的证据。

## 关键决策与取舍

多 Agent 版本出现三类新增问题：分类标签在交接中丢失；多个角色重复读取相同上下文；“质检 Agent 同意”被误当成真实付款状态。团队没有因为角色故事更丰富而采用它。

最终假设方案使用确定性身份/订单检查，加一个 Agent 起草解释；退款动作保留为精确审批。只有当本地任务集证明专门角色能改善某类复杂政策判断时，才考虑增加 Agent。

## 责任、权限与证据

比较报告需固定任务集、模型/工具版本、重复 trial、政策违规、环境结果、延迟和成本。Agent 之间相互同意只能作为过程信号，不能替代订单数据库最终状态和主管决定。

## 结果与限制

本案例没有真实评测分数，也不宣称单 Agent 永远优于多 Agent。它只展示：架构复杂度是一项需要证据的成本，而不是成熟度徽章。

## 可迁移的教训

多 Agent 适合真实的权限隔离、并行独立工作或上下文分区；若只是给同一个模型换五个角色名称，通常增加协调面而没有新证据。
