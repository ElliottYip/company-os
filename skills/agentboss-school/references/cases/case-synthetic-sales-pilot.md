# 合成案例：销售周报 Agent 的试点为什么暂停扩张

> **SYNTHETIC_SCENARIO / ILLUSTRATIVE**：本案例中的组织、角色、事件、系统、指标和结果均为虚构，只用于教学。它不是客户案例或 ROI 证明。

## 业务背景

一家虚构 B2B 服务团队计划让 Agent 从 CRM 和会议摘要生成每周销售风险简报。管理层希望一个月后推广到全部区域，但团队尚未统一“风险客户”的定义。

## 原始工作方式

区域经理各自维护表格，周会上口头说明变化。不同区域使用的阶段、概率和风险标签不一致，CRM 更新也不及时。需求表面是自动写周报，真正问题是业务口径和责任链不稳定。

## Agent 工作设计

试点只覆盖一个自愿参与的小组和只读数据。Agent 输出待核对草稿，逐条列来源时间、缺失字段和冲突；不得更新 CRM、联系客户或承诺折扣。销售运营负责人对简报流程负责，客户负责人确认单条风险。

## 关键决策与取舍

团队先建立人工基线和六类评测任务，包括正常客户、旧数据、相互冲突的会议记录、缺失所有者、未知产品名和要求越权联系客户的文本。周度复盘同时看事实引用、遗漏、人工修订时间、权限事件、延迟和成本。

桌面情境假设前两周发现：生成语言流畅，但许多“风险”只是不同区域定义不一致。正确决定不是增加模型或扩大 rollout，而是暂停扩张，先由业务所有者统一词典和更新责任，再重新跑同一评测集。

## 责任、权限与证据

继续条件、收紧条件和停止条件在试点前写清。任何模拟指标都标记为演练数据。决策记录说明暂停原因来自口径不一致，而不是笼统写“AI 效果不好”。

## 结果与限制

案例没有真实试点、真实时间节省或客户转化结果。暂停扩张是虚构的教学决定，用于说明试点的目标是学习和风险控制，不是证明采购正确。

## 可迁移的教训

AI 往往放大已有数据和流程问题。没有基线、共同定义、流程所有者和退出条件时，漂亮 demo 很容易把组织问题隐藏起来。

## 适合接入的课程节点

- `role/outcome-contract`：把风险简报写成可验收工作；
- `operations/evaluate-and-review`：建立代表性任务和回归；
- `team/pilot`：用证据决定继续、收紧、扩大或停止。
