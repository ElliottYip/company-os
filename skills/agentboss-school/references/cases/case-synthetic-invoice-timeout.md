# 合成案例：付款接口超时后，Agent 想再次提交

> **SYNTHETIC_SCENARIO / ILLUSTRATIVE**：本案例中的组织、角色、事件、系统、数据和结果均为虚构，只用于教学。它不是客户案例，也不是成效证据。

## 业务背景

一家虚构的中型设备服务企业每周处理供应商发票。财务团队希望让 Agent 核对发票、采购单和收货记录，并把无差异项目送入付款流程。真正风险不在字段提取，而在付款接口超时后无法判断银行是否已经受理。

## 原始工作方式

应付专员人工比对三类记录，财务经理批准付款。异常会放进“待查”队列。流程慢但有一个重要安全习惯：银行状态不清楚时先对账，不重新付款。

## Agent 工作设计

Agent 可读取获准的脱敏发票字段、采购单状态和收货标记，输出匹配结果与差异说明。它不得决定供应商主数据变更，也不得自主付款。付款请求绑定金额、币种、收款方标识摘要、发票集合、负责真人和有效期，由财务经理精确审批。

## 关键决策与取舍

一次已批准付款调用在 30 秒后超时。Agent 的通用重试策略建议再次调用。正确决定是把 attempt 标成 `OUTCOME_UNKNOWN`，冻结自动重试，先用原请求 ID 查询银行状态；查询仍不明确时转人工对账。只有确认原动作未发生，才创建新的付款请求和新审批。

## 责任、权限与证据

- 执行 Agent 只能准备和查询本次付款；
- 财务经理对付款决定负责；
- 审批不能复用于修改后的金额或新请求；
- 恢复证据包括原请求摘要、attempt、超时、查询返回和人工对账决定。

## 结果与限制

桌面推演中，团队识别出“超时不等于失败”和“相同技术请求不一定代表相同业务意图”。这只是设计推演，没有真实银行调用、生产结果或节省数据。

## 可迁移的教训

任何发布、付款、创建账户或发送消息的超时，都应先判断副作用是否可能已发生。幂等键、状态查询和对账需要业务语义，不能只靠 Agent 自述。

## 适合接入的课程节点

- `operations/retry-and-outcome-unknown`：练习重试、查询、对账和结果未知；
- `governance/exact-action-approval`：理解旧批准为何不能复用；
- `role/outcome-contract`：把结果未知与禁止静默重试写入合同。
