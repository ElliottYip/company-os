本文件是课程扩建的 canonical 架构。它定义“应该教什么、知识放在哪里、什么证据可以进入课程”，但不替代具体 lesson。`SKILL.md` 继续只做教务路由，具体知识按节点渐进加载。

## 1. 学校边界

AgentBoss School 培养的是对 Agent 工作负责的人，不是特定框架的 Agent 开发者。

课程主线回答六个问题：

1. 什么工作应该交给 Agent？
2. 怎样定义结果、边界、上下文和责任？
3. 怎样观察、介入并可靠地恢复工作？
4. 怎样评测结果、证据和系统行为？
5. 怎样管理权限、数据、安全和高风险动作？
6. 怎样把一次可行实践变成团队可持续运营能力？

模型、Agent 框架、协议和供应商项目只作为实现样本。不得把任何供应商 API 写成完成课程的必要条件。

## 2. 能力模型

保留学习状态中的四个一级能力，增加十二个二级能力。这样现有存档保持兼容，课程可以显著加深。

| 一级能力 | 二级能力 | 能做出的可观察决定 |
|---|---|---|
| `delegation` | 责任模型 | 区分能力、授权、执行与真人责任 |
| `delegation` | 工作设计 | 拆分目标、选择自动化/辅助/委派/真人保留 |
| `delegation` | 结果与上下文合同 | 定义结果、证据、上下文、工具、停止条件与交接 |
| `operations` | 编排模式 | 选择单 Agent、工作流或多 Agent，而不是默认堆 Agent |
| `operations` | 可观测控制 | 读取状态、活动、成本、证据与异常信号 |
| `operations` | 介入与恢复 | 选择等待、澄清、重试、改派、暂停、取消或人工接管 |
| `operations` | 评测与验收 | 建立离线/在线评测、抽样、回归和业务验收证据 |
| `governance` | 权限与身份 | 使用最小权限、短期授权、职责分离和精确审批 |
| `governance` | 数据与安全 | 管理数据范围、出境、Secret、提示注入和工具副作用 |
| `governance` | 事件治理 | 处理结果未知、重复执行、撤销、审计和事故复盘 |
| `team_adoption` | 组织与运营 | 定义角色、运营节奏、升级路径和流程所有者 |
| `team_adoption` | 试点与价值 | 设计基线、指标、成本预算、退出条件和责任移交 |

二级能力不新增到 v1 学习存档的必填字段；lesson 用节点证据映射回四个一级能力，等状态 schema 正式升级时再版本化迁移。

## 4. 知识单元契约

每个 lesson 只解决一个主要管理决定，并必须包含：

1. `学习结果`：可观察行为，而不是“了解”；
2. `核心概念`：稳定定义和必要区分；
3. `决策框架`：何时选择什么，不能只讲原则；
4. `来源`：主张对应来源 ID，不只列延伸阅读；
5. `讲授`：是什么、为什么、怎么用、例子、误区；
6. `失败模式与边界`：何时不适用、可能怎样失败；
7. `实操`：不接生产系统也能完成的决定或工件；
8. `完成证据`：`developing / capable / strong` 的行为标准；
9. `降级路径`：缺产品、网络、案例时仍可教学；
10. `下一节点信号`：按证据路由，不按文件编号机械推进。

每个可检验主张应在 claim map 中有唯一 ID；多个 lesson 可以引用同一主张，但不得复制出互相漂移的定义。

## 5. 来源等级

| 等级 | 来源 | 可以支持什么 |
|---|---|---|
| `A` | 标准、监管/政府指南、同行评审研究、正式技术规范 | 定义、风险、通用控制和已验证研究发现 |
| `B` | 官方产品文档、官方工程文章、开源项目代码/文档 | 特定实现模式、接口行为、工程经验 |
| `C` | 有授权且结果逐条验证的真实案例 | 指定上下文内的实践结果与失败经验 |
| `D` | 高质量二手综述、行业调查、厂商趋势报告 | 背景、待验证趋势和研究线索 |
| `E` | Demo、观点、未验证案例 | 解释性示例和假设，不能证明效果 |

纳入规则：核心安全或治理主张至少需要一个 A 级来源；工程模式至少需要一个 B 级一手来源并注明供应商/版本范围；数量、ROI 和组织效果不能从 Demo 或单一厂商观点推导。

## 6. 冲突处理

先判断冲突属于哪一类：

- **事实冲突**：比较研究设计、发布日期、版本和适用人群；无法消解就并列保留并标 `CONTESTED`。
- **定义冲突**：课程选择一个操作性定义，同时记录其他定义及映射，不宣称唯一正确。
- **工程取舍**：把冲突改写成决策条件，例如单 Agent 与多 Agent、自治与工作流、人审频率与风险。
- **项目政策差异**：明确标成 `AGENTBOSS_POLICY`，不能冒充行业共识。
- **时间冲突**：以当前规范和项目检测到的版本为准，历史模式只用于迁移说明。

不得通过“来源更多”简单投票。最终写入课程的结论必须同时记录：适用范围、反例/限制、证据等级、复核日期和对应节点。

## 7. 课程化流程

```text
发现来源
  → 登记来源与版本
  → 提取最小主张
  → 标证据等级和适用范围
  → 与已有主张做重复/冲突检查
  → 映射到一个主要课程节点
  → 写成决策框架、失败模式和练习
  → 加完成证据与测试
  → 才进入正式课程
```

文章全文和项目文档不直接塞进 lesson 或 RAG。课程保存蒸馏后的知识、短引用和来源 URL；案例正文继续遵守授权、匿名化与证据质量规则。

## 8. 成熟度与认证

- `Foundations`：责任模型、委派、结果合同、精确审批、基础责任闭环。
- `Operator`：生命周期、观察、介入、评测、结果未知和成本控制。
- `Governor`：权限、数据、安全、身份、事故和审计。
- `Team Lead`：角色、运营节奏、试点、价值、改变和移交。

当前签名凭证只证明 `Foundations`，不能因课程扩建自动扩大含义。新增认证必须使用新的 `credentialType` 和独立 rubric。学习路径可跨成熟度自适应，但证书要求必须版本化、公开且不可由付费服务替代。
